# Release notes

One file per release, named after its tag: `v0.1.0.md`. The release workflow publishes the
file at the tag as the GitHub release text (with build and verification details appended), so
write and commit it before tagging.

Shape, for people who use the IDE rather than for developers:

1. One paragraph: what this release brings, in plain words.
2. How to get it (image tag, static site, upgrading from the previous version).
3. `## New: …` sections for the main features, then `## Changes`, `## Fixes` and
   `## Under the hood` as bullet lists with a bold lead (`- **Faster stepping.** …`).

Say what changed for the user and what they can do now, not which files changed.
